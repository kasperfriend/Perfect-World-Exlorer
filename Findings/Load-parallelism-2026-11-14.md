# Startup parallelism and DirectStorage feasibility — 14 November 2026

## Change in this revision

The shared startup CPU gate now defaults to **all logical CPUs reported by the OS**, rather than leaving one permit unused. Terrain-block decode/compression, unique world-model loading and water-texture decode all use that common gate, so their separate worker pools can overlap without each claiming a full machine independently. `PW_LOAD_WORKERS=1..128` remains available to cap or tune the aggregate worker budget. Startup logs the effective budget. A unit test covers both the full-hardware default and explicit overrides.

Using every reported logical CPU is the highest safe general default here, not a guarantee of best wall-clock time on every machine: storage contention, memory bandwidth, thermal limits, and memory pressure can make a lower `PW_LOAD_WORKERS` value faster or more responsive. The existing bounded queues and cache budgets remain important; unbounded task fan-out is intentionally avoided.

## CPU and GPU opportunity assessment

- **CPU:** There is already concurrency across terrain decode, models, water, and other independent asset groups. The shared permit gate prevents those CPU-heavy pools from independently oversubscribing the CPU. This revision removes its default one-core reserve. Static scenery assembly, archive I/O, parsing, terrain cache writes, texture setup and GPU resource creation still contain serial or ordering-sensitive portions; making those parallel requires profiling and bounded ordered pipelines, not simply spawning a thread for every asset.
- **GPU:** The startup path calls `terrain(...)` to finish file parsing and CPU-side preparation before entering `gpu::run(...)`. Consequently, the GPU is not currently available to overlap those startup stages. Once rendering initializes, uploads use wgpu's GPU queue; there is no GPU compute/decompression loader in this project. Moving decompression onto a GPU would first require suitable GPU kernels, format-compatible inputs, upload/staging buffers and a device initialized early. Transfer and synchronization costs can outweigh the benefit for small assets, and current client asset correctness must be preserved exactly.
- **DirectStorage:** The application uses portable wgpu and its current archive reader inflates PCK members with zlib (`src/pck.rs`). DirectStorage is a Windows-specific storage path, not a drop-in acceleration switch for these asset formats. A DirectStorage path would need a compatible Windows/hardware stack, supported archive encoding or a justified conversion/cache format, explicit validation/invalidation, and a fallback for systems without supported hardware. It would not remove scene parsing, resource creation or GPU upload costs. No DirectStorage integration was added because the present pipeline and input formats do not establish that it would accelerate end-to-end startup, and an unvalidated rewrite would risk correctness and portability.

## Limits and next evidence needed

A multi-gigabyte world cannot be guaranteed to load in a fraction of a second: at even 10 GB/s, transferring 5 GB alone has a 0.5-second theoretical lower bound, before decompression, parsing, texture upload, validation and device setup. This project's actual input size and hardware vary, and no client assets or physical target machine were available for a benchmark in this change. “Instant” is therefore not a realistic or verified promise.

The next engineering step for further CPU/GPU tuning is phase timing on representative hardware (file reads, PCK inflate, terrain decode/cache write, model and scenery parse, texture preparation, GPU upload, adapter/device startup), with peak RAM/VRAM and disk throughput. Only then can the dominant phase be optimized without sacrificing quality. GPU compute/decompression or a Windows-only DirectStorage experiment should be considered only if those measurements show a transfer/decompression bottleneck and a matching supported input path.
