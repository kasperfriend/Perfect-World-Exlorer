# Known unsupported or incompletely reproduced client paths

Updated 2 November 2026 against code revision `a9c4b35`. This is an explicit
**nonempty** register, not a claim of an exhaustive asset census. Unknown paths
may still be discovered. Per-requirement evidence and remaining acceptance are
in the [76-point reassessment](Eight-phase-reassessment-2026-11-02.md).

## Known rendering/runtime gaps

| Path / behavior | Remaining limitation | Requirements |
|---|---|---|
| Visual GFX graph and multi-hook chains | The light-producing owner graph is complete for P1.01: scene effects, hook-free ECM `EventType 100` roots and `HookName`-attached roots have a real lifecycle (region load/unload, one root per update, visibility/priority gating, destruction) and attached roots follow the posed skeleton hook every frame (`0x7b25e6` bone × hook, `0x7b2543` model × hook, `0x6e1370` authored hook-local frame). Still open, and owned by the visual-effect graph rather than by light selection: `ChildHook`/`RelHook`/`BindParent` target selection, static `ECMHook` hanger objects (`0x6f89c0`), particle/sprite/trail playback and the authored fade/stop phase of the drawn effect. | P7.04–05 |
| Manager light-priority limit value | The gate and its state are traced and implemented (`0x70ba3c..0x70ba44`: `[element+0xdc] > [manager+0x134]` suppresses publication only, the element keeps progressing and returns alive; the limit is manager-wide, written by `0x40dc97`/`0x40e394`, and survives owner churn/region unload). What is not decoded is the *authored byte* that fills the limit: it arrives through a scene/environment record (`+0xce`, copied from `+0xca` at `0x59af52..0x59af76`) whose file format this reader does not parse, so `Manager::set_priority_limit` defaults to "no suppression" - the client at its highest light setting - instead of an invented threshold that would silently drop authored lights. | P1.01 |
| Controller-108 LUT construction precision | Resolved to PC24. The executable never creates a thread: no `_beginthreadex`/`_beginthread` IAT slot (`0x4d54ec`/`0x4d54f0`) is referenced anywhere in `.text` and `CreateThread` is not imported, so loading is frame-budgeted on the update thread (`0x5b1a00` returns after one root) and construction shares the sampling thread. That thread never changes the x87 control word - `_controlfp` (`0x4d5564`) has no call site and the only `fldcw`/`fnstcw` instructions in the image belong to static CRT math helpers (`0x7fdcb7`, `0x8001e5`, `0x80c878`, `0x863350`) that restore the caller's word - so the device's PC24 word applies. `0x6ec5dd` builds the table with x87 `fmul`/`fsub` only, which under PC24 rounds every intermediate to a 24-bit mantissa; production therefore builds the PC24 table (`gfx_color_track::CONSTRUCTION = Precision::Pc24`). `tools/analyze-color-track-construction.py` still records that the two modes differ (17,790 / 16,332 interior entries of 8,257,536), which bounds the exposure of any root loaded before the device exists (that path would use the startup extended word). | P1.01 |
| Alpha-list depth state | Recovered, no longer an assumption: the alpha/overlay submit path `0x436720` -> `0x436984` -> `0x7844d0` sets SRCBLEND 5 (`0x77a2c0`), DESTBLEND 6 (`0x77a2f0`), **ZWRITEENABLE off** (`0x77a230(0)`), CULLMODE 1 (`0x77a540(1)`) before `0x779ca0(mesh, 1)` submits at `0x78452b`; the tail restores ZWRITE 1 (`0x784678`), CULLMODE 3 (`0x784684`) and the material block (`0x779fc0(0,4)`). ZENABLE is never written in the bracket, so the alpha list keeps the depth **test** and only drops the write; `0x7a76a0`/`0x7a6c30` only override the blend pair and alpha test, and `0x7a7c60` never issues a ZWRITE call, so no blended mesh writes depth. `model_queue` implements this and a regression pins both directions. | P1.02–03 |
| Segmented `LightNum` light elements | Element 130 (`LightType: 1` point light with one keypoint) is executed. The keys once believed to identify a second light family are the effect noise block (`BufLen: %d`, `Amplitude: %f`, `WaveLen: %d`, `Persistence: %f`, `OctaveNum: %d`) plus the line/beam record (`StartPos`, `EndPos`, `Segs: %d`, `LightNum: %d`, `Interval: %d`, `Width: %f`, `Alpha: %f`, `Pos1Enable`/`Pos2Enable`, `UseNormal`, `Normal`, `Filter: %d`). Measured over all 5,459 retail `gfx.pck` roots: 5,878 elements carry one of those keys but only 546 carry `LightType`, and all 546 are element 130. Those elements are therefore **not** light paths and are skipped exactly as the native loader skips their light pass (`0x7078d0` is a separate light-element reader); a root that declares `LightType` on any element other than 130 still fails explicitly with "unsupported GFX light element <id>". Still open and unchanged: the light **strip** those elements rasterise between `StartPos` and `EndPos` belongs to the effect-sprite graph below, so no light is published from them. | P1.01, P7.04 |
| Fixed-function lighting alternative | **Resolved, not applicable.** Every receiving-model mesh submitter turns `D3DRS_LIGHTING` off before its draw (`0x77a3c0(0)` at `0x7a914b`, `0x7a9759`) and restores it in the tail (`0x7a96a3`, `0x7a99f9`); no `0x42b3xx-0x42c7xx` model pass function calls `0x77a3c0` with 1, and the `0x7844d0` alpha/overlay bracket's writes are around the vertex-shader draw. Receiving models therefore never use the fixed-function pipeline, so there is no alternative to implement (`RECEIVERS_USE_FIXED_FUNCTION_LIGHTING`, `src/model_receiver_class.rs`). | P1.02 (closed) |
| Model mesh-level transparency | The current SKI reader exposes no per-mesh transparency field, so the strict-positive transparency override is driven by the frame value the caller supplies. Its native source is unestablished. | P1.02 |
| Special model queue state block | **Resolved, not a model queue.** `0x41a2f0` reads the device wrapper at `[[0x9b3eec]+0x8]` and sets ZENABLE 1 (`0x77a210`), ZWRITEENABLE 1 (`0x77a230`), ALPHATESTENABLE 1 (`0x77a320`), ALPHABLENDENABLE 0 (`0x77a290`), ALPHAFUNC 7 (`0x77a360`), ALPHAREF `0x54` (`0x77a380`), then calls `0x792fc0(arg, 3, 0)`. It is not vtable-only: the address is pushed as the state callback of the dynamic-geometry submitter `0x416ab0` at `0x41a5b5`, and the only maker of that call is `0x41a5a0`, whose sole caller `0x6d17ad` sits in the effect-record draw path (locals `+0x2bc..+0x2e0`). No CECModel mesh submitter passes it, so the block draws alpha-tested, unblended effect sprites and receiving models have exactly the opaque and alpha queues (`SPECIAL_STATE_BLOCK`). The effect-sprite draw itself belongs to the visual-effect graph (P7). | P7 (model scope closed in P1.03) |
| Non-ordinary receiving classes and alpha/special model queues | Ordinary weighted/rigid opaque paths route authored blend pairs into a real alpha queue with retail insertion order, and queue inputs are split by source (model instance: invisible/`+0xc`/blend pair; mesh texture record: `+0x36`/`+0x35`), with non-finite alpha rejected. Morph/supple receiving classes remain explicit errors, which the census shows is a guard for non-retail data: 13,820 skin and 1,988 rigid meshes, zero morph, supple or muscle records. | P1.02 closed for retail data; P7.01–03 |
| Complete regional material consumers | Native coefficient/visibility calculations exist; complete downstream material/celestial consumer coverage is not established. | P1.04–05 |
| Native terrain/grass lightmap residency | Startup metadata and distinct missing-night policies exist; native missing-day retained binding and dynamic load/unload remain open. | P1.06 |
| Static BMD format/material alternatives | Reader accepts the inspected model version and mesh v4/v5, not all versions. All stages, alpha sorting and client overrides are incomplete. | P1.07, P3.01–07 |
| Final postprocess/color/presentation acceptance | Bloom/presenter/sharpen/gamma implementations exist; final pass audit, upstream color coverage and Windows compositor acceptance remain open. | P1.08–09 |
| Complete fog variants | Grass/BMD/terrain refraction paths exist; complete transparent/special-material and underwater ordering coverage is not established. | P1.10, P5.06, P6.07 |
| Native terrain level thresholds, cadence and block flags | The draw window (`0x77ecf0`, `(2r+1)` blocks, edge-shifted), the three-level ladder (`0x77e360`: camera-to-block-centre distance minus `block_size*0.7071067`, two thresholds, no hysteresis) and the coarser-neighbour edge rule (`0x7c40e6`) are implemented per block; the approximate 4-grid far mesh and the seam blend are gone. Still open: the per-block level scale `block+0x7c` is assumed 1.0 (thresholds themselves are decoded: `0x77f450` from `[CECWorld+0x18]+0x60/+0x64`, shipped preset 180/320 world units), the client re-selects levels every frame per view (`0x77e1b0`) while the viewer rebuilds on its 2-block/scene-rebuild trigger, and `block+0x74` visibility is unimplemented. | P2.01–02 |
| Terrain layer sampling | The native state is now implemented exactly: `0x7c14b0` sets MAG/MIN/MIPFILTER = 2 (`D3DTEXF_LINEAR`) and ADDRESSU/V = 2 (`D3DTADDRESS_MIRROR`) on stages 1-5, `0x7c1e00` uses filter 0 / wrap 1 on the fallback stage 0, and `D3DTSS_MAXANISOTROPY`(21) is written nowhere in the terrain path, so the viewer no longer requests 16x. Remaining: D3D8 point-sampled authoring of `D3DTEXF_NONE` cannot be expressed for a wgpu min/mag filter inside a trilinear pipeline without a second sampler, so only the batched (retail) path is exact. | P2.07 |
| Terrain texture formats | Resolved by census. `A3DTexture::CreateDXTExture()` (`0x7f7f74`) forwards the authored FourCC and `0x7f7e4e..0x7f7e71` accepts exactly DXT1..DXT5. The retail `textures.pck` was extracted (117,047,648 bytes, 1038 entries) and every one of the 363 terrain sources (`textures/maps/*.dds`) passes: **DXT3 356, DXT1 7**; 256x256 x235, 512x512 x126, 256x512 x1, 1024x1024 x1. `src/dxt.rs` decodes DXT1..DXT5 and `src/material.rs` keeps the authored chain; anything else is an explicit error naming the file. Non-FourCC DDS (165 in the archive) are non-terrain art and are rejected by the terrain path rather than decoded. | P2.07 |
| Terrain mip chain | Resolved. All 363 terrain sources carry a **complete** power-of-two chain (9/10/11 levels for 256/512/1024) and the payload equals 128 + sum(level sizes) in 363 of 363; **no** source needs generated mips. Production previously decoded to RGB8 (dropping the chain) and box-filtered a fresh one at upload, so level *n* now goes to mip slot *n*. Box reduction remains only for a single-level source, which the client itself treats as `D3DTEXF_NONE`. | P2.07 |

| Terrain layer `type` byte | Each 28-byte T2MK layer record carries a selector at `+12` (values 0/1/2 in `world_39.t2mk` and `world_88.t2mk`) that the native terrain assigns into `[+0x0c]` of its copy of the record and passes to `0x77f180` (`0x7a2589..0x7a25b9`) when it builds the draw list. The viewer reads the same byte but treats it as the texture projection axis (`axis`); the two meanings have not been separated, so no new behaviour is claimed for it. | P2.08 |
| Terrain holes and visibility/special-surface flags | Still unimplemented, and deliberately not invented. ## Completion policy

P8.10's **tracking/policy deliverable** is implemented by maintaining this register;
that does **not** mean its entries are resolved. P8.01's exhaustive census and
resolution requirement remains incomplete. Do not claim 100% parity while this
register has open entries, while the census is incomplete, or while full-scope
acceptance gates remain open. Removing rows, renaming gaps, or passing compilation
cannot satisfy that condition. Close entries only with implemented behavior and
specific validation evidence.

This register records behavior-level gaps. Existing named asset/dependency failure
reporting in `world_models.rs` and client survey manifests remains necessary;
this document does not replace a complete per-asset failure census.
